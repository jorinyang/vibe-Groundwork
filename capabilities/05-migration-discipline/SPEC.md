# 数据迁移纪律

## 为什么

没有它，schema 变更会散落成一次性脚本，数据库状态无法从仓库重现。更隐蔽的坏法是「有了迁移注册表但顺序是错的」——看起来有工程化，实际全新部署建不起来库。

## 必须达到的行为

| # | 断言 | 怎么观测 | rigor |
|---|---|---|---|
| 1 | 不存在含 SQL 的一次性脚本 | 扫 `deploy/` `scripts/` `tools/` 下 `apply-*` 等命名的文件，检查是否含 DDL/DML 或数据库客户端调用 | static |
| 2 | 存在版本化迁移来源 | 迁移目录，或代码内迁移注册表 | static |
| 3 | 迁移声明顺序与序号单调一致 | 抽迁移名里的序号，检查数组声明顺序是否递增 | static |
| 4 | 不碰数据库的项目不判失败 | 若项目无任何 DDL / SQL 文件 / 迁移目录，判 `N/A` | static |
| 5 | **迁移真的落库了** | 配了 `dbPath` 就打开 SQLite，检查 `_migrations` 表存在且有条数 | behavioral |

第 5 条需要 `.vibe/config.yaml` 里有 `dbPath`；没有则标 `[待配置]`。非 SQLite 数据库暂不支持该探针。

## 怎么验

```bash
node src/cli.ts check --path <项目目录>
```

期望：sw-ims 判 FAIL（两条规则），YSCOT 判 N/A。

## 常见抄错

| 抄法 | 为什么不算通过 |
|---|---|
| 有 `migrations.ts` 但数组顺序乱的 | 全新数据库会在建表前先改表，初始化直接失败 |
| 把数据修复写成 `apply-xxx.mjs` 一次性脚本 | 仓库里缺这条变更，换个人部署就漏 |
| 一次性脚本里只调 API 不写 SQL | 那是部署脚本，不算迁移问题——**不能误伤** |
| 项目根本不碰数据库却要求有迁移目录 | 过度要求，判 N/A |
