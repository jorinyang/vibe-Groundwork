## 二、做对了什么

1. **判定抓到了真 bug。** SW-IMS 的 54 条迁移声明顺序与序号相反，全新数据库初始化会失败——这是「文件存在性检查」永远发现不了的问题，因为它有 `migrations.ts`，形状完全正确。
2. **误报被真实项目抓出来并修掉 4 条。** 每条都记在 `REPORT-validation.md` 里，包括最尴尬的两条：检查器扫自己时把自己的正则字面量当成 `app.get("*")`、把 SQL 关键字当成建表。
3. **`N/A` 被当成一等的结论。** 不碰数据库的项目、依赖没装的项目、工具链缺失的项目，都判 `N/A` 并给原因，不被强行塞进 `fail` 或 `pass`。
4. **修复闭环真的闭环了。** 在 SW-IMS 副本上：快照 → 生成 AGENTS.md → 补 11 个环境变量 → 复扫，宪法 FAIL 转 PASS，全程可回滚。

## 三、必须修（Must Fix）

1. **规格缺口：最大的债没有判定覆盖。**
   SW-IMS 的 `deploy/` 下有 60+ 个一次性部署脚本（每个功能一个 `apply-*.sh`），这是最真实的工程化债。但六项能力里**没有任何一项覆盖它**——迁移纪律只查「含 SQL 的脚本」，这些是部署脚本。
   → 需要新增 `deploy-discipline`：部署是否可复现、是否一条命令、回滚是否可用。这是当前最大的规格漏洞。

2. **三项判定低于自己的 DoD。**
   `migration-discipline`、`project-constitution`、`env-contract` 都是 `static`（5 分），标准要求核心判定 ≥ 8。要么升级为 behavioral，要么把它们明确降级为「基础项」，不能挂在核心表里假装达标。

3. **行为判定从未在真实项目上跑通。**
   健康检查、权限默认拒绝的行为探针，在所有样本上都是 `N/A`——因为样本项目都没有 `.vibe/config.yaml` 的启动配置。**这些代码路径等于没被验证过。** 需要在至少一个真实项目上配好启动命令跑通一次。

## 四、应该修（Should Fix）

1. **`check.yaml` 与实现可能漂移**：目前 yaml 是文档，代码是事实。要么让引擎读 yaml，要么在 CI 里校验两者一致。
2. **`vibe fix` 跑两遍完整检查**（执行前 + 复扫），大项目上慢一倍。可以只复扫受影响的能力。
3. **MCP server 没有对真实客户端测过**：只用脚本模拟过 JSON-RPC，没接过真实 agent 客户端。
4. **没有 Python 真实样本**：Python 只在合成 fixture 上验证过。

## 五、可以优化（Could Improve）

1. 报告加「与上次相比」的趋势——工程化是长期的事，单次快照看不出退化。
2. `--json` 输出加 schema 版本号，方便下游消费。
3. 能力清单加 `since` 迁移说明，判定升级时能告诉用户「这次判定变严了什么」。

## 六、蓝军审查（挑毛病）

**死亡假设 1：agent 会主动用这套工具。**
不会。agent 只在被要求时跑检查。如果没有 CI 门禁把它变成硬约束，这套东西就是可选的 —— 而可选的规范等于没有规范。
*缓解*：CI 门禁已做（P2），但需要真实接入一个项目才算验证。

**死亡假设 2：六项能力能代表「工程化」。**
不能。六项覆盖的是「起步阶段最容易出事的六件事」，不是全部。当前最大的漏洞是部署纪律（见 Must Fix 1）。

**死亡假设 3：判定器自己不会腐化。**
会。检查器扫自己时已经自伤两次。需要把「自检」变成常规门禁（已加 CI），并且每次加能力都要在自身跑一遍。

**未被验证的前提**：`N/A` 率高达 50%（18/36）——如果真实使用中 `N/A` 一直是这么高，用户会觉得「跑了个寂寞」。需要统计「配置完成后 N/A 率能降到多少」。
