## 7.2 蓝军审查

### Phase 1 · 本质还原

**核心价值主张（比方案本身更深一层）**

不是「检查项目有哪些文件」，而是：**「工程化做完了没有」这件事，第一次有了可执行、可复现的判定，而且这个判定能被 agent 直接消费。**

真正的付费点（这里是时间与注意力）：**替人做判断**。人不想读 54 条迁移、不想数 60 个脚本，他要一句「能不能上线、还差什么」。

| 方案说我们要做… | 这只是手段 | 真正的目的是… |
|---|---|---|
| 六项能力判定 | 手段 | 把「工程化完成」变成可验收 |
| 处方（prescription） | 手段 | 把修复成本从人转移到 agent |
| MCP / Skill | 手段 | 让 agent 能主动取用，而不是人记得去跑 |
| conformance spec | 手段 | 让判定被别人复用，而不是自娱自乐 |

**反本质信号**
- 把「能力条数」当成「覆盖度」（6 项 ≠ 工程化）
- 把「42 次判定」当成「验证充分」（样本同源）
- 把「闭环跑通」当成「有人会用」

### Phase 2 · 死亡假设

**前提条件扫描**

| # | 方案假设 | 如果为假的影响 |
|---|---|---|
| 1 | 用户愿意花时间先跑一次检查 | 整条价值链路不成立 |
| 2 | 6 项能力足以代表「工程化」 | 用户觉得「你只管了边角」 |
| 3 | agent 会主动调用这套工具 | 判定永远不执行 |
| 4 | **判定的误报低到可被信任** | **一次误报 = 永久流失** |
| 5 | N/A 不会多到让人觉得「跑了寂寞」 | 价值感知为零 |
| 6 | agent 真的会抄「模板」 | 运行时能力永远落不了地 |
| 7 | 判定能被长期维护 | 半年后判定腐化，标准失去信用 |

**最脆弱的假设（Load-bearing）**

> **假设 4：判定的误报低到可被信任。**

死因场景：一个陌生开发者第一次跑，看到 3 个 FAIL，其中 1 个他不认同（比如「你凭什么说我的 README 不可运行」）。**开发者工具的信誉是一次性的**——第一次被冤枉，后面全绿他也不信了。

而这条假设在本项目上**已经被证伪过四次**：部署脚本误判、依赖缺失误判、扫自己自伤、Windows 编码导致识别失效。

**Tiger 分级**

| 级别 | 死亡假设 | 理由 | 应对 |
|---|---|---|---|
| 🐯 **Tiger** | 误报毁信任 | 概率高（已实测翻车 4 次），影响致命（信誉一次性） | 异构样本扩充 + 每条判定公布误报率 + 首次运行默认只出报告不阻断 |
| 🐯 **Tiger** | N/A 率过高 | 当前 19/42 = **45%**，用户会觉得没验到东西 | 报告必须区分「不适用」与「未配置所以无法判定」，并给出配置指引 |
| 📄 Paper Tiger | 「没人用」 | 确实可能，但这是分发问题不是设计问题；开源工具默认没人用是常态，为此改设计是错的 | 记录，不投入设计资源；靠 npx 降摩擦即可 |
| 🐘 Elephant | 六项覆盖不到最大债 | SW-IMS 的 60+ 部署脚本没有任何能力覆盖 | if-then：一旦有第二个用户提出「我的问题是部署」，立刻加 `deploy-discipline` |
| 🐘 Elephant | 判定腐化 | 半年后没人维护，判定变成噪音 | if-then：spec 加版本号 + 每次改判定必须同步 CHANGELOG |

### Phase 3 · 苏格拉底追问

**追问链 1 · 判定可信度**

> **Q1**：第一次运行如果有 1 条误报，用户会不会继续用？
> *预期回应*：会解释说是「边界情况」。
> **Q2**：那你怎么保证误报率？6 个样本够吗？
> *预期回应*：不够，而且其中 5 个是同一个作者的 Node monorepo，**样本同源**。
> **Q3**：换一个完全不同的栈（Rails / Go / Java）呢？路由抽不到会发生什么？
> *答案*：路由抽不到 → 权限判定直接 N/A → 用户看到「全绿或全 N/A」→ 误以为项目没问题。**这是最危险的失败模式：沉默的绿灯。**

**追问链 2 · 价值定位**

> **Q1**：用户为什么不直接用 ESLint + SonarQube + OpenAPI lint？
> **Q2**：如果六项里三项还是静态判定，你和 ESLint 的本质区别是什么？
> *诚实回答*：**目前区别没有宣传的那么大。** 真区别在「处方」和「给 agent 用」，但 F2 只实现了两个 green 动作（建 AGENTS.md、补 .env.example），自动修复的覆盖面很薄。
> **Q3**：那所谓「自愈闭环」是真能力还是演示？

**追问链 3 · 采用闭环**

> **Q1**：新人怎么拿到这个工具？现在要 `git clone` 再 `node src/cli.ts`。
> **Q2**：跑完看到 4 个 FAIL，其中 2 个他不懂为什么要改，谁来解释？
> *答案*：他现在得自己去读 `SPEC.md`——报告里只有一句 message，没有「为什么这是问题」。
> **Q3**：如果解释成本高于修复成本，他会不会直接忽略？

### Phase 4 · 三维挑战

**挑战 1 · 业务伪命题**

- 声称痛点：vibecoding 项目缺工程化
- 可观测改变：项目里多出 AGENTS.md、`.env.example` 补齐、迁移顺序修正、CI 有门禁
- **判断：真实痛点，但混淆了两件事**——「缺工程化」是事实，「愿意花时间补工程化」是意愿。工具解决的是后者，而后者阻力更大。**判定能发现问题 ≠ 人会去修。**

**挑战 2 · 商业闭环（开源形态）**

- 价值创造：省下「这个项目能不能上线」的判断时间 ✓
- 价值交付：**断在这里**——要 clone、要 Node 22.6、要自己配启动命令。摩擦大于感知价值。
- 价值捕获：开源捕获注意力 → star / 使用者 / 后续机会。当前没有 npx 一行命令、没有 demo 截图、没有 before/after 对比。
- **断环结论**：交付环节断裂。

**挑战 3 · 服务陷阱**

- 好消息（README 会写的）：6 项能力、MCP、闭环、42 次判定、0 误报
- 坏消息（执行中会发生的）：真实用户第一跑大概是 Python/Go/Java 项目 → 大量 N/A → 「这东西没用」
- 被忽略的人群：非 Node 用户、非 HTTP 项目、**已经工程化得不错的项目**（跑完全绿，然后呢？没有「下一步」）

### Phase 5 · 重构 + KPI

**必须修复（来自 Tiger 级）**

| # | 问题 | 重构方案 | KPI | 验证方法 |
|---|---|---|---|---|
| 1 | 交付摩擦高 | 发布到 npm，`npx vibe-check check --path .` 一行跑 | 从看到 README 到第一份报告 ≤ 2 分钟、步骤 ≤ 1 步 | 找 3 个没接触过的人冷启动计时 |
| 2 | 样本同源 | 补 3 个不同栈、不同作者的真实项目 | 覆盖 ≥4 种框架；异构样本上误报率 ≤10% | 在扩充后的样本上重跑，统计 FAIL 的人工复核通过率 |
| 3 | N/A 不透明 | 报告区分「不适用」与「未配置无法判定」，并给配置指引 | 配置完成后 N/A 率 < 20% | 在 SW-IMS 上配好 `.vibe/config.yaml` 后重跑 |
| 4 | 解释成本高 | 报告每条 FAIL 内联一句「为什么这是问题」（来自 SPEC 的「为什么」段） | 100% 的 FAIL 自带原因，不看 SPEC 也能懂 | 抽样 10 条 FAIL 让人判断是否理解 |

**建议改进**

| # | 问题 | 改进建议 | 预期效果 |
|---|---|---|---|
| 1 | 规格缺口 | 新增 `deploy-discipline`（部署可复现、一条命令、可回滚） | 覆盖 SW-IMS 最大的债 |
| 2 | 三项 rigor 低于门槛 | 迁移纪律升 behavioral（真起库验 `_migrations`） | 核心判定均分 ≥8 |
| 3 | 没有"下一步" | 全绿时输出「你已到 L3，下一步可以做 L4 治理项」 | 让好项目也有获得感 |
| 4 | 无 demo | README 加 SW-IMS 的 before/after 报告对比 | 降低理解成本 |

## 🟢 站得住脚的部分

- **判定确实抓到了真 bug**（迁移顺序）——这是文件存在性检查永远发现不了的
- **误报被真实项目抓出并修掉 4 条**，且每条都有记录
- **`N/A` 被当成一等的结论**，没有强行塞进 pass/fail
- **红灯不可自动改**这条约束守住了，权限能力只出 patch
- **栈无关设计成立**：Python 项目用同一套判定跑通，没有额外适配代码

## 💡 一句话

**这个方案的技术是成立的，但它的生死不在技术，在两件事：让判定永远不冤枉人，以及让人愿意跑第一遍。**

修这两条之前，不要做第七项能力。
